## 1. 验证明文部署、审计与协议可行性

本节决定生产路径和依赖，证据记录在本 change 的 `validation.md`，只保留脱敏的环境类型、命令、结果和版本信息。缺少真实目标记录必须写“未验证”，不能勾选通过。验证不通过时按 design 的处理分支收敛；不得静默减少三平台范围或增加联网、提权、凭证前提。联网包管理器安装只作为用户明确选择的可选路径，不能替代离线基线验证。后续基础夹具可以独立准备，但不能把尚未验证的路径作为可发布能力。

- [ ] 1.1 明确代表性目标审计的记录方式与验收口径，列出检测、安装/部署及安装脚本行为、复检、启动、采集、取消、失败的预期记录，以及是否需要逐文件路径；取得实际审计样本并记录差异。
- [ ] 1.2 在 Linux 目标验证已有工具检查及离线普通用户明文首次部署，记录基础命令、Shell/OS/架构、组件来源/版本/许可/摘要；证明没有编码命令或隐藏执行。
- [ ] 1.3 在 macOS 目标完成同等明文部署验证，记录系统工具、执行限制和支持架构，不以 Linux 结果替代。
- [ ] 1.4 在 Windows 目标完成同等明文部署验证，覆盖未编码 PowerShell 与执行策略限制，不改用 EncodedCommand 或策略绕过。
- [ ] 1.5 以固定版本候选完成双跳 SSH、tmux、Linux 容器/WSL 及审计链路的文件往返验证，核对内容和目录结构；确认 `trzsz` 元数据编码与默认 Ctrl+C 启动的适配要求。
- [ ] 1.6 用最小验证程序证明新实例绑定、接收器提前退出、SSH 退回上一层、已排队输入和迟到帧的停止发送行为；同时验证三平台固定明文采集的有限执行范围与结束证据。
- [ ] 1.7 确定生产协议/单用途组件、版本锁定、平台基础条件、分块/未确认窗口/解压/超时预算及审计信息呈现方式；将证据回填 design，若无法满足硬约束则先修订方案而不进入不合规生产路径。

- [ ] 1.8 在三平台验证 `trz` / `tsz` 分方向的路径、版本和运行能力检查模板，覆盖只有一侧可用、同名非兼容命令、超时无结束证据、执行受限、安装后 PATH 未更新及用户目录绝对路径；记录最低兼容版本与能力要求。
- [ ] 1.9 为各平台整理通过审计验证的完整安装方案和复制命令，声明来源/固定版本/位置/基础工具/联网/权限条件；可选包管理器方式必须验证安装内部行为，没有通过验证的方案不提供快捷执行。
